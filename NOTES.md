# MacShade – development notes

See [README.md](README.md) for usage. These notes describe how it works and which pitfalls cost time.

## Architecture in one sentence
The unmodified ReShade 6.8 core (`reshade/`) runs as `libmacshade.dylib` inside an ad-hoc re-signed copy of the game (`DYLD_INSERT_LIBRARIES`);
`mac/platform/*` replaces everything Windows-specific.

## Building blocks (`mac/platform/`)
- `dll_main_mac.cpp` + `late_init_mac.cpp`: paths (early, in the first object file), log/config (late, in the last object file) — **link order matters**.
- `vk_loader_emulation.cpp`: plays the Vulkan loader (layer chain, dispatch keys for instance/device/queue/command buffer) and replaces ~140 MoltenVK symbols by
  jump stubs via dyld interposing (`vk_stub_list.inc`, generated by `gen_vk_stubs.py`) and `dlsym`.
  Note: dyld also applies interposing to `dlsym` results — fetch the real functions through `vk_icdGetInstanceProcAddr`, never through `dlsym("vkGetInstanceProcAddr")`.
- `input_mac.mm`: swizzles `-[NSApplication sendEvent:]` → Windows VK key state, mouse position in pixels, cursor capture, GameController.
  Only keys that are ReShade shortcuts wake the bridge from idle (otherwise every WASD press would flash ReShade's own FPS counter).
- `gl_bridge_mac.mm` / `metal_bridge_mac.mm` / `vk_bridge_mac.cpp`: bridge for OpenGL/Metal (IOSurface ↔ private Vulkan device; ReShade's back buffer is replaced via
  `swapchain_impl::_override_image`, then `reset_effect_runtime`/`init_effect_runtime`). The bridges switch themselves off as soon as the app uses Vulkan directly.
  - *Pipelined mode*: ring of 3 IOSurfaces, GL fences (APPLE_fence on legacy contexts, `glFenceSync` on core profiles — the core path is untested), result shown two frames late.
  - *Idle bypass*: with no active effect, closed overlay and no statistics, the bridge leaves the game's frame alone and draws its own FPS counter.
  - *Depth*: OpenGL — the game's scene FBO is found, copied into an R32F IOSurface; Metal — depth attachments are remembered and converted. ReShade sees the "DEPTH" semantic
    (`g_macshade_depth_srv` overrides the built-in depth add-on). The OpenGL search takes the smallest matching framebuffer below ID 128 — only validated with UT2004.
- `frame_limit_mac.cpp`: optional frame limiter (`MACSHADE_FPS_LIMIT`).
- `dll_resources_mac.mm` + `localization_data.inc` (`gen_strings.py`): embedded shaders/fonts/texts, 16 languages (system language automatically).
- `compat/mac_compat.h`: Win32 shims, type-unique `__uuidof` (ReShade uses it as a key for private data!).
- `debug_mac.cpp`: `MACSHADE_CRASH_TRACE` (backtrace even for games with their own crash handler).

## Pitfalls
- A game seems to hang: the macOS "restore windows" dialog after an aborted test → pass `-ApplePersistenceIgnoreState YES` (the launcher does).
- A game seems to hang at start: an unanswered macOS permission prompt (e.g. screen recording) can block it.
- Objective-C objects in globals without ARC → use-after-free (the bridge files are built with `-fobjc-arc`).
- Hardened runtime blocks injection → always run an ad-hoc signed copy; some games (Quetoo) restore their original signature, so the launcher re-checks before every start.
- Tests: never kill a game you did not start yourself.
  Never take full-screen screenshots (private content): use `work/winid2.swift <name> <pid>` + `screencapture -l`.
- lldb attach/launch hangs on this setup and leaves `debugserver` processes → use `MACSHADE_CRASH_TRACE` and the crash reports in `~/Library/Logs/DiagnosticReports`.
- `CRT.fx` (SweetFX) with *Curvature* on renders black through MoltenVK — the Retro presets keep curvature off.

- Quake3e's Vulkan renderer (`quake3e-vulkan`) runs on MoltenVK without ReShade, but with ReShade attached `vkQueueSubmit` returns `VK_ERROR_DEVICE_LOST` right after start, even with no technique enabled. Its OpenGL build works through the bridge. Not investigated further (suspects: the immediate command list flush in ReShade's `vkQueueSubmit` hook, device creation extras).

## Open points / ideas
- Games with a statically linked MoltenVK (Raze): the Metal hook would have to handle `-[CAMetalDrawable present]` including command-buffer synchronisation.
- Depth for OpenGL/Metal on more games; real Metal depth from a game is still unverified.
- Gamepad (GameController) and fullscreen cursor capture are untested with real hardware.
- Core-profile OpenGL (`glFenceSync` path) is untested.

## Vulkan apps that bundle the real loader (Spider-Man: Edge of Time recomp)
Apps that ship `libvulkan.1.dylib` + MoltenVK as an ICD (volk, plume) never expose MoltenVK to `dlsym`, so the emulated loader had nothing to hook. `my_dlsym` now also serves `vk*` lookups from a real loader through the emulated one, and `ensure_mvk` loads our own MoltenVK (`MACSHADE_MOLTENVK`) when no ICD is loaded yet. Result: ReShade overlay and effects work in the unmodified (ad-hoc re-signed) copy. Verified only with EdgeOfTimeRecomp 1.0.0 on an M5.

## Screen filter mode (capture_filter_mac.mm)
Opt-in per game (`Game.captureMode`). `Launcher.startFiltered` opens the original app through `NSWorkspace` and starts `MacShadeFilter` (`App/Helper/MacShadeFilter.m`, a few lines that `dlopen` libmacshade and call `macshade_filter_main`). The helper captures the game's window with an `SCStream` (BGRA IOSurfaces), blits each frame into a private work surface, runs `macshade_bridge_process` on it, copies the finished frame into one of five display surfaces that the window server is not using (`IOSurfaceIsInUse`) and sets that as `contents` of a borderless window on the game window's frame (polled four times a second, one level above the game's own window level).
Lessons: (1) never process in place in a surface that may be on screen: that showed unfiltered frames between filtered ones (flicker, menu appearing and vanishing; measured with a test window: 15 of 40 captures filtered before, 40 of 40 after). (2) keep the chosen game window while it exists and debounce restarts: games have several windows, switching restarts the capture and rebuilds the ReShade runtime. (3) accept any window level: borderless "full screen" windows sit above level 0.
Overlay and effect toggle are global Carbon hotkeys (no extra permission) that call `macshade_bridge_set_overlay` / `_toggle_effects`, applied on the rendering thread. While the overlay is open the window takes mouse and keyboard, afterwards the game is activated again.
Verified with the unmodified Spider-Man: Edge of Time recomp (no injection), a test window (windowed, macOS full screen, level-25 borderless) and hotkeys sent as system key events. Not verified: real keyboard, mouse interaction with the menu, exclusive full screen (display capture), the Screen Recording permission of a signed MacShade.app (tests ran under the terminal's permission).

## Minimum macOS of the injected library
`libmacshade.dylib` is loaded into games and must load on every macOS the app supports (13 and later). It used to be built with the host's SDK and deployment target (macOS 27), so releases 0.1-0.4 failed to load below macOS 27 (status 1, "built for macOS 27 which is newer than running OS"). `mac/CMakeLists.txt` now sets `CMAKE_OSX_DEPLOYMENT_TARGET 13.0` and makes unguarded newer APIs an error for the Objective-C++ files. (0.4.1 to 0.4.4 claimed this but the flag was hidden by `-w`; since 0.4.5 the target uses `-Wno-everything`, and the check really finds e.g. `SCStreamFrameInfoBoundingRect`, which exists only on macOS 14.) Floating-point `std::from_chars`/`to_chars` (macOS 26 / 13.3) were replaced by `strtof`/`snprintf` in ReShade's effect lexer and GLSL/HLSL codegen. Check a build with `vtool -show-build <dylib>` (minos 13.0). Not tested on a real older macOS.

## Screen filter: half resolution
`captureHalfResolution` (Performance tab, off by default) passes `--scale 0.5` to the helper, which asks ScreenCaptureKit for half the pixel size; the window shows it enlarged. Measured only with a test window (1470x956 instead of 2940x1912 frames processed), no FPS numbers.

## Screen filter: geometry and diagnostics (0.4.3)
Report: on a Mac mini with an external monitor the picture was about 96 % of the screen, anchored bottom left, and clicks landed beside the buttons (full screen via the green button and via the game). Cause not found; not reproduced. Changes: the overlay window no longer lets AppKit move or shrink it (`constrainFrameRect:toScreen:`), the frame is cropped to `SCStreamUpdateFrameContentRect` when ScreenCaptureKit reports margins, and the log now has the game window, wanted and actual overlay frame, all screens with scale, the captured frame size and a 10 s summary (frames in/shown/dropped, ms per frame). `MACSHADE_FILTER_DEBUG=1` additionally logs the frame attachments once. Effects switched off with the effects hotkey did not slow the filter down in a test (58 fps, 3.4 ms per frame).

## Screen filter 0.4.4: pipeline, bypass, hotkeys, geometry log
- **Pipeline** (`MACSHADE_PIPELINE`, set from the game's "smooth frame rate" option): three ring surfaces; frame n is copied (not awaited), n-1 goes to ReShade (`macshade_bridge_pipeline_submit`), n-2 is shown. When the capture is quiet the last frame is fed again up to three times so the pipeline empties. Measured on a GPU-bound scene: no reliable gain (about 20 to 23 fps); the copy waits for the GPU behind the game (8-30 ms), ReShade itself needs 2-7 ms.
- **Idle bypass**: when `runtime::is_idle` (effects off, menu closed) the capture is stopped and the overlay hidden, the game runs unfiltered; a hotkey ends it (`MACSHADE_FILTER_NO_BYPASS=1` disables it).
- **Hotkeys** (menu, effects, screenshot) are system-wide Carbon hotkeys, registered only while the game (or the helper, menu open) is frontmost. The screenshot key asks ReShade's runtime for its own screenshot (`runtime::request_screenshot`), named after the game.
- **Geometry**: attachments are read through the SDK constants; every change of surface size, bounding/content rect, contentScale, scaleFactor and screenRect is logged, as is the capture size (`pointPixelScale` on macOS 14+, else the screen's backing scale). Reported but not found: picture 96 % of the window on a Mac mini with an external monitor.

## 0.4.5
- `SCStreamFrameInfoBoundingRect` (macOS 14) and `SCStreamFrameInfoScreenRect` (macOS 13.1) are guarded with `@available`; before 0.4.5 reading a missing key would have crashed the filter on macOS 13. Without the bounding rect there is no crop.
- The crop is `(content.origin - bounding.origin) / bounding.size`.
- Frame rate limit in screen filter mode: it sets `minimumFrameInterval` (the captured, so the filtered, picture); the helper no longer sleeps after each frame. The game itself is not limited (another process); the game page says so.

## 0.4.6: the window as ScreenCaptureKit sees it
Report (Mac with a 1920x1080 display, macOS 15): the filtered picture was 96 % of the window, black bar on top, strip on the right, clicks beside the buttons. The frame attachments showed `contentScale 0.9609`, `contentRect 1844.8x1080 pt`, surface 1920x1080 at `scaleFactor 1`: ScreenCaptureKit shrank the window to fit, so it sees the window as 1844.8/0.9609 x 1080/0.9609 = 1920x1124 pt, 44 pt taller than the window list says (a title bar above the top of the display; the black bar and the strip in the old screenshot match: 44 x 0.9609 = 42 px, 1920 - 1844.8 = 75 px). The 0.4.3 crop divided `contentRect` by `boundingRect` (equal) and cropped nothing. Now:
- crop = `contentRect * scaleFactor` (pixels per point) / surface size;
- source size = `contentRect / contentScale`; when it is larger than the window list's size the overlay is extended by the difference (assumed above the window, so the extra part lies above the screen edge, `constrainFrameRect:` already allows that) and the capture is restarted at that size so nothing is shrunk;
- the geometry log ignores the moving window position (a sliding full-screen window used up the 12 lines), and logs the derived values;
- half resolution is enlarged with a linear filter (nearest-neighbour looked like a stretched video).
Verified with `MACSHADE_FILTER_FORCE_SIZE=1920x1080` on a 1000x632 window (reproduces the shrink: `contentScale 0.8544`, content at the left of the surface) and with a borderless window 44 pt above the screen. Not verified: the reporter's case itself (the window list and ScreenCaptureKit agreed on the height in every test here), and that the extra height is above the window.

## Measured: ReShade directly on the game's frames (not worth it)
The pipelined bridge copies each frame into a private work image and back (`vk_bridge_mac.cpp`, `record_copy`). `MACSHADE_BRIDGE_STATS=1` now also logs the GPU time of both copies (Vulkan timestamps): about 0.55 ms in + 0.6 ms out at 2940x1912, i.e. ~30 % of the bridge's GPU time with the light Look preset.
Tried the alternative: the three IOSurface frames as ReShade's back buffers (ReShade supports several back buffers natively via `get_back_buffer_count`/`get_current_back_buffer_index`, so no runtime reset per frame). It worked, but the total GPU time was the same within noise (Look 3.9 vs 3.9 ms, Sharp-Only 3.3 vs 3.15 ms, Cinematic 3.9 vs 3.6-4.4 ms): ReShade is slower on an IOSurface-backed image than on a private optimal-tiled one and eats the saved copies. Not kept (the experiment was removed again). Measured on a battery-powered MacBook with a synthetic window, so only a rough result.

## Screen filter: fewer copies, dynamic resolution
GPU time per frame at 2940x1912 (Look preset, synthetic window, MacBook on battery; `MACSHADE_BRIDGE_STATS=1` shows the Vulkan side, the filter log line "GPU time of the Metal copies" the Metal side):
- before: Metal blit in 0.9-1.1 ms + Vulkan copy in 0.55 + ReShade 2.4 + Vulkan copy out 0.6-0.9 + Metal blit out 1.2-1.8 = about 5.4-7 ms
- now: the captured IOSurface is read by Vulkan itself (imported per surface id, held with its CMSampleBuffer until the slot's job is done; queueDepth 6) and ReShade's copy-out goes straight into the display surface (five surfaces imported once): about 3.4 ms, no Metal copy left. Same picture (marker test, crop offsets with the fake title bar still right).
- `MACSHADE_FILTER_METAL_IN=1` brings back the Metal copy in, `MACSHADE_FILTER_METAL_COPY=1` both Metal copies (for comparison or if a system misbehaves).
- Not verified: macOS versions other than the development one, real games, many window resizes in a row.

Dynamic resolution (`--dynamic`, game page toggle "Dynamic resolution", off by default, ignored with half resolution): once a second the filter thread's busy share is measured. Above 0.55 for 3 s: one step down (100 -> 90 -> 75 %). A step up only when the estimated load of the higher step (busy x pixel ratio) is below 0.44 for 10 s; 6 s pause after each change. A change restarts the capture (short flicker). `MACSHADE_DYN_DOWN=<x>` moves the thresholds (test aid). The step down was exercised with lowered thresholds (100 -> 90 %, clean restart); the step up and the real thresholds were not tried under real GPU load.

## Metal games (Mush8, a Switch emulator): slow with ReShade even with the effects off
Measured with `MACSHADE_BRIDGE_STATS=1` ("Present rate of the game", "Bridge GPU split"), game started with the library injected, attract mode, 1920x1080 drawable (the reporter's was 2940x1846, 2.6x the pixels).
Causes found:
1. No bypass while only ReShade's FPS counter was on (MacShade turns `ShowFPS` on by default) and none at all in the synchronous Metal path: every frame went through two Metal copies plus two Vulkan copies for nothing. About 1.1 ms (Vulkan side) plus the Metal blits at 1080p, so roughly 5 ms or more at the reporter's size.
2. A tutorial that was never started kept `runtime::is_idle` false for ever (`_tutorial_index == 0`), so a fresh instance never bypassed. Now ignored on macOS (`runtime.cpp`).
3. The pipelined path presented with a plain `presentDrawable:` and so dropped the game's `presentDrawable:afterMinimumDuration:` pacing: the emulator then ran uncapped (about 100 fps in light scenes instead of its 50). Now the game's own call (plain, at time, after minimum duration) is used for the processed frame.
4. While nothing is drawn the game's present is no longer deferred to the end of its command buffer (`pass_through_now`, `MACSHADE_NO_PASS_THROUGH=1` switches that off).
Result in the same scenes: effects off 50 fps flat like without MacShade (before: 100 fps unpaced, or full copy cost); effects on 50 fps flat. With effects on the bridge still costs about 3.4 ms GPU per frame at 1080p (about 9 ms at 2940x1846) on top of the game: a GPU-bound game loses frame rate there. Next step would be what the screen filter does (let Vulkan read and write the drawable's IOSurface instead of the four copies, about 45 % less).
Not tried: the effects hotkey inside this game (the key presses sent by automation did not arrive), heavy race scenes.
Metal games are no longer pipelined by default (`Game.pipelineMetal`, env `MACSHADE_PIPELINE_METAL`): two frames more delay were noticeable (racing/action) and the game keeps its own pacing; OpenGL keeps `pipeline` (default on). Metal depth buffers exist only in the pipelined mode, so effects that need depth need the second toggle. Checked with Mush8: default = synchronous Metal bridge, 50 fps flat; with the toggle = pipelined, 50 fps flat.
Metal bridge, idle: the layer's `framebufferOnly` (set to NO so ReShade can read drawables) goes back to YES after about 180 frames of pass-through, so Core Animation can optimise display again; a frame fetched in that state is presented without processing. Mush8 (new build, 2940x1846, effects off, 3 runs each): GPU utilisation 46.7 % with this vs about 50 % (46.5-54.2) before vs 45.9 % without MacShade; the rest is noise. Not verified in a real race.

## Game page: start buttons and looks (UI)
"Start ReShade" plus a separate "Normal start" (`Launcher.startPlain`: opens the original app with the saved start parameters, no copy, no injection). The Look tab lists the looks compactly (name, "Activate look" checkbox = the one active look, Details): `LookCard` in `Looks.swift`. Details: effect explanation, look name (rename for own looks, "Save as new look" for the default and included ones) and the shader choice (`TechniqueCatalog.scan` reads `technique X` from the collections' .fx files; `Presets.setTechniques` rewrites the `Techniques=` line, the rest of the preset stays). Uninstall: the card and the first dialog now say that the whole game is deleted (to the Trash). Checked by eye in the running app; rename / save as / add shader were not run end to end.
